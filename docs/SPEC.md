# Техническое задание: WireGuard TUI SSH

## 1. Статус документа

Черновик технического задания для реализации AI-агентом.

Название приложения и CLI-команды: `wgtui` (финальное, см. п.30.1).

Язык интерфейса только английский. Архитектура строк должна позволять добавлять новые локализации без изменения бизнес-логики.

## 2. Краткое описание продукта

Необходимо разработать универсальное консольное приложение с TUI для Linux и macOS, которое управляет одним или несколькими удалёнными WireGuard-серверами через SSH.

Приложение должно:

- подключаться к серверу по SSH;
- использовать SSH-ключ, `ssh-agent` или интерактивный пароль;
- обнаруживать установленный WireGuard и существующие интерфейсы;
- читать и анализировать текущую конфигурацию без раскрытия серверного приватного ключа;
- показывать состояние сервера, интерфейсов и peers;
- показывать handshake, endpoint и текущие счётчики трафика;
- создавать клиентские профили локально;
- добавлять, приостанавливать, возобновлять, перевыпускать и удалять peers;
- экспортировать готовый `.conf` локально и показывать QR-код;
- при отсутствии WireGuard предложить установить его штатным способом;
- при отсутствии настроенного сервера предложить безопасный мастер первоначальной настройки;
- работать без Web UI, Docker, постоянно запущенного агента и дополнительного открытого административного порта на сервере.

Основной принцип продукта:

> На удалённом сервере остаются только стандартный WireGuard, стандартные системные конфигурации и SSH. Управляющая логика находится в локальном приложении.

## 3. Цели

### 3.1. Основные цели

1. Упростить безопасное управление обычным WireGuard-сервером без ручного редактирования `/etc/wireguard/*.conf`.
2. Не требовать установки отдельной панели управления на сервер.
3. Не требовать ручного входа на сервер и скачивания клиентских конфигураций через `scp`.
4. Поддерживать существующие WireGuard-инсталляции, а не только серверы, созданные приложением.
5. Предоставить интерактивный TUI и неинтерактивный CLI/JSON-интерфейс для автоматизации и AI-агентов.
6. Выполнять изменения транзакционно: резервная копия, проверка, применение, постпроверка и откат при ошибке.
7. По умолчанию не хранить пароли и не передавать приватные ключи без необходимости.

### 3.2. Неосновные цели первой версии

В первую версию не входят:

- собственная реализация протокола WireGuard;
- замена официальных WireGuard-клиентов;
- Web UI;
- облачный control plane;
- регистрация пользователей по email;
- LDAP/Active Directory/OIDC;
- биллинг и квоты;
- постоянная серверная база статистики;
- автоматическая настройка домашнего/офисного роутера;
- Windows-клиент управляющего приложения;
- mesh-сеть уровня Tailscale/Netmaker;
- обязательный серверный daemon.

## 4. Термины

- **Управляющий клиент** — приложение `wgtui`, запущенное на Linux или macOS администратора.
- **Удалённый сервер** — Linux-машина, на которой работает или будет установлен WireGuard.
- **Интерфейс** — WireGuard-интерфейс, например `wg0`.
- **Peer** — сущность WireGuard, идентифицируемая публичным ключом.
- **Профиль** — клиентский `.conf`, содержащий клиентский приватный ключ.
- **Активный peer** — peer присутствует в работающем интерфейсе и постоянной конфигурации.
- **Приостановленный peer** — доступ отозван с сервера, но метаданные и локальный профиль сохранены для возможного восстановления.
- **Удалённый peer** — доступ отозван; его метаданные удалены по подтверждению пользователя.
- **Full tunnel** — весь клиентский трафик направляется через VPN.
- **Split tunnel** — через VPN направляются только выбранные сети.

WireGuard не имеет встроенных «пользователей», логинов, сессий или статуса online. В UI допустимо использовать слово «пользователь» как удобное представление peer, но внутренняя модель обязана учитывать реальные свойства WireGuard.

## 5. Поддерживаемые платформы

### 5.1. Управляющий клиент

Обязательно:

- Linux amd64;
- Linux arm64;
- macOS amd64;
- macOS arm64/Apple Silicon.

### 5.2. Удалённый сервер

MVP:

- Ubuntu Server с systemd;
- Debian с systemd;
- Fedora Server с systemd.

Следующая очередь:

- несколько WireGuard-интерфейсов с разными системами запуска.

macOS является платформой управляющего клиента, но не серверной платформой.

## 6. Архитектурные принципы

### 6.1. Отсутствие постоянного серверного компонента

Приложение не должно устанавливать на сервер:

- `wgtui-agent` или другой daemon;
- Web UI;
- Docker/Podman;
- Node.js/Python runtime специально для приложения;
- веб-сервер;
- отдельную систему аутентификации;
- постоянно работающий сборщик статистики в MVP;
- дополнительный слушающий TCP/UDP-порт.

Допустимы:

- официальные пакеты WireGuard из репозитория ОС;
- стандартные конфигурационные файлы WireGuard;
- стандартный sysctl drop-in для forwarding;
- резервные копии конфигурации;
- небольшой файл несекретных метаданных, если пользователь включил эту возможность;
- временный скрипт или временный файл на время одной SSH-операции при гарантированном удалении.

### 6.2. Управление через SSH

Все удалённые операции выполняются через существующий SSH-доступ. Не открывать дополнительный административный порт.

Предпочтительная реализация MVP — системный OpenSSH-клиент, уже установленный на Linux/macOS. Это позволяет использовать:

- `~/.ssh/config`;
- SSH aliases;
- `ssh-agent`;
- macOS Keychain;
- `ProxyJump`;
- аппаратные ключи;
- стандартный `known_hosts`;
- существующую корпоративную SSH-политику.

Если позднее будет выбран встроенный SSH-клиент, он обязан корректно реализовать host-key verification и не уступать системному OpenSSH по безопасности.

### 6.3. Разделение секретов

- Приватный ключ сервера создаётся и хранится только на сервере.
- Приватный ключ нового клиента создаётся и хранится только на управляющей машине/у владельца профиля.
- На сервер передаётся только публичный ключ клиента.
- На управляющую машину передаётся только публичный ключ сервера.
- Пароль SSH/`sudo` не сохраняется приложением по умолчанию.
- Приватные ключи не должны попадать в логи, диагностические отчёты, crash dump или JSON-вывод.

## 7. Решение вопроса с клиентскими `.conf`

### 7.1. Обязательная схема для новых профилей

Клиентский конфиг не создаётся на сервере и поэтому не требует скачивания.

Алгоритм:

1. `wgtui` локально генерирует клиентский private key.
2. Локально вычисляет public key.
3. По SSH отправляет серверу только public key и назначенный VPN-адрес.
4. Сервер добавляет peer в WireGuard.
5. `wgtui` локально собирает готовый клиентский `.conf`.
6. Профиль сохраняется локально с правами `0600`.
7. Пользователю предлагаются действия:
   - сохранить в выбранный каталог;
   - показать QR-код в терминале;
   - скопировать конфигурацию в буфер обмена;
   - открыть системный диалог сохранения, если он доступен;
   - вывести только публичную информацию.

Преимущества:

- не нужен `scp`;
- клиентский private key не попадает на сервер;
- не нужны временные клиентские файлы на сервере;
- компрометация сервера не раскрывает приватные ключи клиентов;
- конфиг доступен сразу после создания peer.

### 7.2. Криптографическое ограничение

Сервер WireGuard хранит public key клиента, но не его private key. Поэтому невозможно восстановить ранее созданный клиентский `.conf`, если private key не сохранился локально.

Для существующего peer приложение должно показывать один из статусов:

- `profile available` — локальный профиль найден и его public key совпадает;
- `profile not available` — сервер знает peer, но локального private key нет;
- `profile mismatch` — локальный файл найден, но его ключ не совпадает с сервером.

Если профиль потерян, правильная операция — **перевыпуск**:

1. создать новую пару ключей;
2. заменить public key на сервере;
3. сформировать новый локальный `.conf`;
4. старый public key окончательно отозвать.

Приложение не должно обещать «скачать» или «восстановить» профиль, которого нет.

### 7.3. Локальное хранилище

Профили по умолчанию сохраняются вне исходного кода и вне обычных логов.

Единый переносимый каталог приложения на Linux и macOS:

```text
~/.wgtui-config/vault.json
```

Профили и метаданные находятся внутри одного зашифрованного vault. Старые
XDG/Linux и macOS пути переносятся атомарно при первом запуске новой версии.
Явный TUI-экспорт создаёт в домашнем каталоге bundle вида
`DimaOffice_WireGuard/` с файлами `DimaOffice.conf` и `DimaOffice_QR.png`.
Это не считается внутренним состоянием приложения.

Требования:

- каталог `0700`;
- файлы профилей `0600`;
- атомарная запись через временный файл;
- понятное предупреждение при сохранении в синхронизируемый каталог;
- запрет на запись поверх существующего файла без подтверждения;
- локальный реестр не должен содержать private key отдельно от самого профиля;
- TUI-экспорт только в домашний каталог запустившего пользователя;
- bundle-каталог `0700`, `.conf` и QR PNG `0600`, без перезаписи.

Пароли не сохранять в локальном реестре. Путь к SSH private key сохранять можно, сам ключ копировать нельзя.

### 7.4. QR-код

QR-код строится локально из готового профиля встроенной Go-библиотекой. Не требовать установки `qrencode`.

Перед показом предупредить, что QR-код содержит private key и является секретом. Не записывать QR в лог. PNG создаётся только после явного действия export и записывается с mode `0600` рядом с `.conf`.

## 8. Рекомендуемый технологический стек

Основной язык: Go.

Причины:

- один бинарник без runtime;
- простая кросс-компиляция;
- удобная работа с процессами, SSH и терминалом;
- подходящие библиотеки для TUI и QR;
- удобное тестирование;
- низкие требования к ресурсам.

Рекомендуемые компоненты:

- TUI: Bubble Tea;
- компоненты TUI: Bubbles;
- стили: Lip Gloss;
- QR: библиотека, работающая полностью локально;
- конфигурация приложения: TOML или JSON;
- структурированный вывод: JSON;
- секреты: только память процесса и защищённые локальные файлы;
- выполнение SSH: системный `ssh` в MVP.

Не использовать shell как основной язык приложения. Shell допустим только как небольшой встроенный удалённый адаптер для атомарной работы с системной конфигурацией.

### 9.3. Статусы peer

- `online` — свежий handshake по заданной эвристике;
- `idle` — handshake был, но давно;
- `never_connected` — handshake отсутствует;
- `disabled` — peer приостановлен управляющим приложением;
- `unmanaged` — обнаружен в WireGuard, но отсутствует в локальном реестре;
- `drifted` — активная и постоянная конфигурации расходятся;
- `error` — состояние невозможно корректно определить.

Порог `online` должен быть настраиваемым. Значение по умолчанию: handshake не старше 180 секунд.

## 10. SSH и аутентификация

### 10.1. Мастер подключения

Поля:

1. SSH alias или hostname/IP.
2. Порт, по умолчанию `22`.
3. Пользователь.
4. Метод входа:
   - SSH agent/настройки OpenSSH;
   - файл private key;
   - интерактивный пароль.
5. Требуется ли `sudo`.

Если введён SSH alias, приложение должно сначала использовать `ssh -G <alias>` и показать вычисленные host/user/port, не раскрывая секреты.

### 10.2. Host key

- Строгая проверка `known_hosts` включена по умолчанию.
- При первом подключении показать fingerprint и запросить подтверждение.
- При изменении host key остановить подключение с явным предупреждением.
- Не использовать `StrictHostKeyChecking=no`.

### 10.3. Пароль

- Не принимать пароль аргументом CLI.
- Не помещать пароль в environment variable.
- Не выводить пароль в PTY capture или debug log.
- Не сохранять пароль после завершения процесса.
- Для `sudo` инициировать интерактивный `sudo -v`, после чего использовать `sudo -n` в пределах текущего SSH-сеанса/ControlMaster.
- Кнопка «забыть авторизацию» должна закрывать SSH ControlMaster и очищать память процесса.

### 10.4. Привилегии

Read-only диагностика должна максимально выполняться без `sudo`. Административные операции требуют явного подтверждения и `sudo`/root.

Приложение не должно автоматически создавать passwordless sudoers rule. В будущем можно вывести отдельно проверенную инструкцию для ограниченного sudo, но не применять её без явного запроса.

## 11. Первичное обнаружение сервера

После SSH-подключения выполнить read-only discovery.

### 11.1. Система

- `uname -srm`;
- `/etc/os-release`;
- наличие `systemctl`, `rc-service`;
- пакетный менеджер;
- архитектура;
- текущий пользователь и возможность `sudo`;
- доступное дисковое пространство в `/etc` и `/var`.

### 11.2. WireGuard

- наличие `wg`;
- наличие `wg-quick`;
- `wg --version`;
- `wg show interfaces`;
- `wg show all dump`;
- конфиги `/etc/wireguard/*.conf` без передачи private key;
- systemd units `wg-quick@*`;
- права и владелец конфигов;
- наличие `SaveConfig = true`;
- расхождение runtime и persistent state.

### 11.3. Сеть

- адреса и маршруты;
- default route и outbound interface;
- `net.ipv4.ip_forward`;
- IPv6 forwarding;
- слушаемые UDP-порты;
- конфликт порта WireGuard;
- nftables/iptables/UFW/firewalld;
- существующий NAT;
- VPN-подсети, конфликтующие с предполагаемой подсетью WireGuard.

### 11.4. Результаты discovery

Возможные состояния:

1. `WireGuard missing`.
2. `Tools installed, no interfaces configured`.
3. `Configuration exists, interface stopped`.
4. `Interface active and configuration consistent`.
5. `Runtime/config drift detected`.
6. `Unsupported or ambiguous configuration`.
7. `Insufficient privileges`.

До любых изменений показать краткий отчёт и предложенные действия.

## 12. Установка WireGuard при его отсутствии

### 12.1. Общий принцип

Если `wg` отсутствует, приложение предлагает:

```text
WireGuard не найден.

[1] Только установить WireGuard
[2] Установить и запустить мастер настройки сервера
[3] Показать команды без выполнения
[4] Отмена
```

Никакая установка не начинается автоматически.

### 12.2. Разрешённые пакеты

Устанавливать только официальный пакет WireGuard/`wireguard-tools` и его обязательные зависимости из настроенного репозитория ОС.

Не устанавливать:

- Docker;
- Web UI;
- PiVPN;
- сторонние management scripts;
- `curl`, `jq`, Python или Node.js только ради приложения;
- новый firewall, если в системе уже есть рабочий backend.

### 12.3. Адаптеры установки

Ubuntu/Debian:

```bash
sudo apt-get update
sudo apt-get install wireguard
```

Fedora:

```bash
sudo dnf install wireguard-tools
```

Другие дистрибутивы добавлять отдельными протестированными адаптерами. Не угадывать пакетную команду только по наличию бинарника package manager; учитывать `/etc/os-release`.

Перед установкой:

- показать определённый дистрибутив;
- показать точную команду;
- запросить подтверждение;
- по возможности показать dry-run/план зависимостей;
- зафиксировать, что существующие пакеты не удаляются.

После установки проверить:

```text
wg доступен
wg-quick доступен
kernel/module support доступен
версия определена
```

Если пакет требует перезагрузки ядра, не перезагружать сервер автоматически. Сообщить пользователю и завершить установочный шаг.

## 13. Мастер первоначальной настройки WireGuard-сервера

Запускается только если WireGuard установлен, но подходящий серверный интерфейс отсутствует, либо пользователь явно выбрал создание нового интерфейса.

### 13.1. Вводимые параметры

- имя интерфейса, по умолчанию `wg0`;
- VPN IPv4 CIDR;
- необязательный IPv6 CIDR;
- UDP port, по умолчанию `51820`;
- endpoint hostname/IP;
- outbound interface;
- режим по умолчанию: full tunnel или split tunnel;
- DNS для клиентских профилей; по умолчанию Google Public DNS `8.8.8.8, 8.8.4.4`, с возможностью явной замены пользователем;
- включение forwarding;
- NAT для full tunnel;
- автозапуск;
- путь сохранения локальных профилей.

### 13.2. Автовыбор VPN-подсети

Предложенная подсеть не должна пересекаться с:

- адресами интерфейсов сервера;
- маршрутами сервера;
- локальной сетью SSH-клиента, если её можно безопасно определить;
- уже существующими VPN-подсетями.

Перед применением показать выбранную подсеть и найденные потенциальные конфликты.

### 13.3. Серверные ключи

- server private key генерируется на сервере с `umask 077`;
- файл/конфиг получает права `0600`;
- private key не возвращается в приложение;
- приложение получает только server public key;
- не использовать private key в командной строке.

### 13.4. Конфигурация интерфейса

Создание `/etc/wireguard/<interface>.conf` выполняется транзакционно.

Минимальный шаблон:

```ini
[Interface]
PrivateKey = <SERVER_PRIVATE_KEY>
Address = <SERVER_VPN_ADDRESS>
ListenPort = <UDP_PORT>
```

Для full tunnel дополнительно требуется forwarding и NAT. Реализация должна учитывать текущий firewall backend.

### 13.5. Firewall/NAT

Порядок:

1. Определить активный backend: nftables, iptables, UFW или firewalld.
2. Прочитать существующие правила.
3. Не сбрасывать таблицы и цепочки.
4. Добавить только необходимые правила.
5. Создать резервную копию затрагиваемой конфигурации.
6. Показать план до применения.
7. Проверить правила после применения.

Запрещено:

```bash
iptables -F
iptables -t nat -F
nft flush ruleset
ufw reset
```

Если backend не поддерживается безопасно, приложение должно остановить автоматическую настройку, показать необходимые ручные действия и не оставлять частично настроенный сервер.

### 13.6. IP forwarding

Использовать отдельный sysctl drop-in, например:

```text
/etc/sysctl.d/99-wgtui-wireguard-forward.conf
```

Не перезаписывать `/etc/sysctl.conf` целиком. До изменения проверить существующие значения и конфликты.

### 13.7. Запуск

Для systemd:

```bash
sudo systemctl enable --now wg-quick@<interface>
```

Проверить:

- interface active;
- адрес назначен;
- UDP port слушается;
- forwarding включён;
- NAT присутствует;
- SSH-соединение осталось доступным.

### 13.8. Роутер

Приложение не может гарантированно настроить внешний роутер. Оно должно сформировать точную инструкцию:

```text
Protocol: UDP
External port: <UDP_PORT>
Internal IP: <SERVER_LAN_IP>
Internal port: <UDP_PORT>
```

Также показать предупреждения о CGNAT, double NAT и необходимости DHCP reservation/static LAN IP.

## 14. Чтение конфигурации без утечки server private key

Запрещено передавать полный `/etc/wireguard/<interface>.conf` на управляющую машину, если в нём есть `PrivateKey`.

Допустимые методы:

1. Получать runtime state через `wg show ... dump`, где private key должен быть отфильтрован.
2. Выполнять серверный parser/redactor, заменяющий значение `PrivateKey` интерфейса до вывода.
3. Выполнять изменение конфигурации сервер-side временным скриптом, который не печатает секрет.

Redactor обязан учитывать пробелы, регистр параметров и несколько интерфейсов. Тесты должны доказывать отсутствие private key в stdout/stderr/debug logs.

## 15. Управление постоянной конфигурацией

### 15.1. Источники состояния

Нужно различать:

- runtime state ядра (`wg show`);
- persistent config (`/etc/wireguard/<interface>.conf`);
- локальные метаданные `wgtui`;
- локальные клиентские профили.

UI должен явно показывать drift между ними.

### 15.2. Транзакция изменения

Каждая операция add/disable/resume/delete/rotate должна:

1. получить блокировку интерфейса;
2. повторно прочитать fingerprint текущей конфигурации;
3. отказаться от изменения, если файл изменился после предварительного чтения;
4. создать timestamped временную recovery-копию на сервере;
5. создать новый конфиг во временном файле на том же filesystem;
6. сохранить владельца и mode исходного файла;
7. проверить синтаксис через штатные WireGuard tools;
8. атомарно заменить файл;
9. применить конфигурацию без остановки остальных peers;
10. проверить runtime и persistent state;
11. при ошибке восстановить recovery-копию и повторно синхронизировать runtime;
12. после успеха или проверенного rollback удалить recovery-копию и временные файлы;
13. сохранить recovery-копию и показать её удалённый путь только если автоматическое
    восстановление само завершилось ошибкой;
14. освободить блокировку.

Предпочтительное live-применение — `wg syncconf`, подготовленное через `wg-quick strip`, поскольку оно не должно без необходимости разрывать соединения остальных peers.

### 15.3. Блокировка

Если доступен `flock`, использовать lock file в `/run/lock`. Если `flock` отсутствует, использовать атомарное создание lock directory. Старую блокировку нельзя удалять без проверки PID/времени и подтверждения.

### 15.4. SaveConfig

`SaveConfig = true` может перезаписать ручные изменения при остановке интерфейса. Приложение обязано обнаруживать его и:

- показать предупреждение;
- использовать совместимый режим;
- либо предложить миграцию на управляемую конфигурацию;
- никогда не менять его молча.

### 15.5. Комментарии и неизвестные параметры

Parser/writer должен сохранять:

- комментарии;
- порядок неизвестных полей;
- `PreUp`, `PostUp`, `PreDown`, `PostDown`;
- `Table`, `MTU`, `DNS`, `FwMark` и иные поддерживаемые поля;
- секции peers, которыми приложение не управляет.

Нельзя регенерировать весь файл из ограниченной внутренней модели и терять неизвестные строки.

## 16. Метаданные и имена peers

WireGuard не имеет поля имени peer. Возможны два режима.

### 16.1. Локальные метаданные — обязательный MVP

Локальный реестр связывает:

```text
server-id + public-key -> name, notes, profile path, created_at, status
```

Неизвестные peers отображаются по VPN-адресу и сокращённому public key.

### 16.2. Удалённые несекретные метаданные — optional

Пользователь может разрешить создать один файл, например:

```text
/etc/wireguard/.wgtui-meta.json
```

Он не является программой или daemon и не содержит private keys. Он нужен для одинаковых имён и статусов при управлении сервером с нескольких компьютеров.

Требования:

- только public key, имя, заметка, дата, статус и VPN-адрес;
- mode `0600`, root-owned;
- атомарные изменения и временная recovery-копия;
- приложение работает и без него;
- повреждение metadata не должно ломать WireGuard;
- WireGuard config остаётся источником истины для доступа.

## 17. Операции с peers

### 17.1. List

Показать:

- имя;
- VPN-адрес;
- сокращённый public key;
- статус;
- latest handshake;
- endpoint;
- RX/TX;
- наличие локального профиля;
- active/persistent drift;
- тип маршрутизации профиля, если он известен.

### 17.2. Add

Поля мастера:

- имя;
- интерфейс;
- автоматический или ручной VPN-адрес;
- full/split tunnel;
- дополнительные AllowedIPs;
- DNS, значение по умолчанию `8.8.8.8, 8.8.4.4`, которое пользователь может осознанно заменить;
- PersistentKeepalive;
- срок действия optional, только как metadata в MVP;
- путь локального экспорта;
- optional preshared key.

`PresharedKey` — дополнительный 256-битный симметричный секрет, который WireGuard
смешивает с обычным public-key handshake. Он не заменяет `PublicKey`, не обязателен
для безопасности WireGuard и включён по умолчанию как дополнительный слой. Его нужно
защищать так же, как private key; он не попадает в логи, планы и обычные экраны.

Проверки:

- уникальность имени в локальном реестре;
- уникальность public key;
- отсутствие пересечения `/32` с другим peer;
- адрес входит в серверную VPN-подсеть;
- endpoint и server public key известны;
- порт корректен;
- файл назначения не существует.

После add показать профиль и ожидать handshake, не утверждать, что соединение работает до фактической проверки.

### 17.3. Disable/Pause

Семантика:

- удалить peer из runtime;
- удалить peer из persistent config;
- сохранить локальный профиль;
- сохранить public metadata со статусом `disabled`;
- не освобождать VPN-адрес автоматически;
- не удалять private config.

После перезагрузки сервера peer не должен появляться снова.

### 17.4. Resume

- проверить, что VPN-адрес и public key не заняты;
- вернуть peer в persistent config;
- применить runtime;
- обновить metadata;
- дождаться handshake по желанию пользователя.

### 17.5. Delete/Revoke

Операция должна отдельно запросить:

```text
1. Отозвать доступ на сервере?
2. Удалить локальный профиль с private key?
3. Удалить metadata?
```

По умолчанию отзыв сервера не удаляет локальный файл. Удаление файла требует явного подтверждения точного пути.

### 17.6. Rotate/Reissue

Используется при утрате или компрометации профиля.

Безопасный порядок:

1. локально создать новую пару ключей;
2. создать новый локальный профиль во временном файле;
3. транзакционно заменить public key peer на сервере;
4. проверить persistent/runtime state;
5. атомарно переименовать новый профиль в итоговый;
6. старый локальный профиль переместить в карантин или удалить по подтверждению;
7. дождаться нового handshake.

### 17.7. Import local profile

Пользователь может выбрать существующий `.conf`. Приложение локально вычисляет public key из private key и пытается сопоставить профиль с peer сервера.

Private key при этом не передаётся серверу и не выводится в лог.

## 18. Full tunnel и офисный внешний IP

Приложение должно поддерживать оба режима, но чётко объяснять различие.

Full tunnel IPv4/IPv6 leak protection:

```ini
DNS = 8.8.8.8, 8.8.4.4
AllowedIPs = 0.0.0.0/0, ::/0
```

Каждый новый профиль должен содержать явный IPv4 DNS по умолчанию. Профиль не должен зависеть от DNS, полученного текущей Wi-Fi, Ethernet или мобильной сетью. Это особенно важно при `::/0`, если сервер предоставляет только IPv4-выход. Отдельный профиль для iOS только из-за DNS создавать нельзя: один и тот же корректно сформированный профиль должен импортироваться официальными клиентами WireGuard на iOS, Android, Linux, macOS и Windows.

Один профиль разрешено переносить между устройствами, но одновременно активировать его можно только на одном устройстве. Для одновременной работы устройства обязаны иметь разные пары ключей и VPN-адреса.

Split tunnel example:

```ini
AllowedIPs = 10.10.0.0/24, 192.168.88.0/24
```

Для full tunnel необходимо проверить:

- IPv4 forwarding на сервере;
- NAT/MASQUERADE через outbound interface;
- FORWARD rules;
- endpoint route на клиенте обрабатывается WireGuard-клиентом;
- отсутствие IPv6 leak;
- DNS availability.

В мастере создания профиля показывать:

```text
Full tunnel: весь интернет клиента будет выходить через сервер.
Split tunnel: через сервер пойдут только выбранные сети.
```

### 18.1. Эталонный сценарий Office 308

Для проверки продукта использовать существующий сценарий:

```text
Endpoint: nas.paynet.one:51820/UDP
Server VPN IP: 10.10.0.1/24
Expected client public IPv4 in full-tunnel mode: 94.200.113.114
```

Критерий: после импорта созданного full-tunnel профиля внешний IPv4 клиента должен быть `94.200.113.114`.

## 19. Статистика и понятие online

WireGuard предоставляет текущие значения:

- latest handshake;
- remote endpoint;
- bytes received;
- bytes sent;
- allowed IPs;
- persistent keepalive.

WireGuard не поддерживает постоянную пользовательскую сессию. Поэтому UI не должен утверждать «подключён» только на основании наличия peer.

Статистика трафика runtime может сбрасываться после:

- перезагрузки;
- перезапуска интерфейса;
- удаления и повторного добавления peer.

MVP показывает текущие счётчики и явно подписывает их как runtime counters.

Исторические графики без постоянно работающего сборщика невозможны. Возможное расширение — optional exporter/agent, но оно не входит в базовый режим и не должно устанавливаться автоматически.

## 21. CLI и автоматизация

TUI не должен быть единственным интерфейсом.

Примеры:

```bash

wgtui server inspect office
wgtui server install-wireguard office
wgtui server configure office

wgtui peer disable office Alex
wgtui peer enable office Alex
wgtui peer rotate office Alex
wgtui peer revoke office Alex

wgtui diagnose office
```

Для destructive/mutation команд:

- интерактивное подтверждение по умолчанию;
- `--yes` только для автоматизации;
- `--dry-run` обязателен;
- `--json` для структурированного результата;
- коды возврата должны быть документированы;
- private keys и пароли запрещены в JSON.

Пример JSON peer:

## 22. Диагностика

Команда `diagnose` должна быть преимущественно read-only.

Проверки:

- SSH reachability;
- host key;
- sudo availability;
- WireGuard tools;
- service active/enabled;
- interface exists;
- UDP listen port;
- runtime/persistent peer drift;
- duplicate public keys;
- overlapping AllowedIPs;
- duplicate client VPN IP;
- forwarding;
- outbound route;
- NAT/MASQUERADE;
- firewall forwarding;
- endpoint DNS resolution на локальной машине;
- внешний порт: только ограниченная UDP-эвристика;
- состояние аварийной recovery-копии;
- права на конфиги;
- `SaveConfig` risk;
- локальные profile/key mismatches.

Нужно объяснять ограничения:

- случайный UDP-пакет не вызывает нормальный ответ WireGuard;
- timeout не доказывает открытый порт;
- `Connection refused` обычно указывает на закрытый или неправильно проброшенный UDP-порт;
- окончательная проверка — свежий handshake;
- handshake не доказывает full tunnel;
- внешний IP проверяется на подключённом клиенте.

Автоисправление выполняется только отдельной командой после показа плана.

## 23. Безопасность

### 23.1. Обязательные требования

- Никогда не использовать `StrictHostKeyChecking=no` по умолчанию.
- Никогда не писать password/private key в аргументы процесса.
- Маскировать секреты в stdout/stderr.
- Устанавливать `umask 077` для операций с ключами.
- Удалять временные файлы через `defer`/trap.
- Не следовать симлинкам при записи системных файлов.
- Проверять владельца и mode конфигурации.
- Использовать абсолютные проверенные пути.
- Не выполнять shell-команду, составленную прямой конкатенацией пользовательского ввода.
- Валидировать interface name, IP/CIDR, port, public key и пути.
- Использовать безопасную передачу stdin или строгое quoting.
- Не разрешать path traversal в именах профилей.
- Не использовать имя пользователя как shell fragment.
- Проверять fingerprint файла перед записью для защиты от concurrent modification.
- Создавать временную recovery-копию до mutation.
- Удалять её после успешной проверки или проверенного rollback; сохранять только при
  ошибке автоматического восстановления.

### 23.2. Имена

Отображаемое имя может содержать Unicode и пробелы. Имя файла должно формироваться отдельным sanitizer:

- запрет `/`, `\0`, `..` как path element;
- ограничение длины;
- разрешение коллизий;
- пользователь видит итоговое имя файла до записи.

### 23.3. Логи

Логировать:

- время;
- server-id;
- тип операции;
- interface;
- сокращённый public key;
- результат;
- путь recovery-копии только при состоянии `recovery required`;
- диагностические коды.

Не логировать:

- private keys;
- preshared keys;
- passwords;
- полный профиль;
- содержимое QR;
- необработанный `/etc/wireguard/*.conf`.

Debug mode не отменяет эти ограничения.

## 24. Ошибки и восстановление

### 24.1. Потеря SSH во время изменения

- Не выполнять новую mutation вслепую.
- После восстановления SSH повторно выполнить discovery.
- Сравнить runtime, persistent config и сохранённую recovery-копию, если она осталась.
- Показать состояние `recovery required`.
- Предложить завершить транзакцию или восстановить конкретную recovery-копию.

### 24.2. Ошибка применения runtime

- восстановить persistent config из временной recovery-копии;
- попытаться синхронизировать runtime из recovery-копии;
- проверить SSH;
- не перезапускать весь сервер;
- вывести точный безопасный план ручного восстановления.

### 24.3. Ошибка создания локального профиля

Если peer уже добавлен, но локальный профиль не удалось сохранить:

- private key держать в памяти до выбора нового пути;
- не завершать операцию как успешную;
- предложить сохранить повторно;
- при отмене предложить автоматически отозвать только что созданный peer;
- не оставлять неизвестный активный peer без явного решения пользователя.

### 24.4. Recovery restore

Если автоматический rollback не удался, восстановление всегда показывает точный
удалённый путь сохранённой recovery-копии и diff. Перезапуск `wg-quick@...` допускается
только после предупреждения, поскольку он кратковременно отключит всех peers.

## 25. Нефункциональные требования

- Время запуска локального TUI: до 1 секунды без подключения к серверу.
- Первичное read-only discovery обычного сервера: целевое значение до 5 секунд после SSH-аутентификации.
- Один бинарник для каждой платформы.
- Отсутствие telemetry по умолчанию.
- Работа в терминалах без true color.
- Корректное поведение при изменении размера терминала.
- Поддержка клавиатуры без мыши.
- Доступный plain mode без полноэкранного TUI.
- Все mutation операции идемпотентны либо безопасно отказываются от повторения.
- Unit tests не требуют root.
- Integration tests выполняются в изолированных VM/container/network namespace.
- Покрытие критической логики parser/transaction/security — не менее 80%.

## 27. Критерии приёмки MVP

MVP принят, если выполнены все условия:

1. Один бинарник запускается на Linux и macOS.
2. Можно подключить сервер по SSH alias, key и интерактивному паролю.
3. Host key проверяется безопасно.
4. Приложение обнаруживает отсутствие WireGuard.
5. На Ubuntu/Debian и Fedora оно предлагает и после подтверждения устанавливает только WireGuard packages.
6. Оно умеет настроить новый `wg0` на поддерживаемой чистой VM.
7. На сервер не устанавливается постоянный компонент приложения.
8. Оно обнаруживает существующий `wg0` и показывает peers.
9. Server private key не передаётся локально и не появляется в логах.
10. Новый client private key создаётся локально.
11. Готовый `.conf` появляется локально без `scp` и без server-side client file.
12. QR-код генерируется локально.
13. Add peer не отключает существующих peers.
14. Pause сохраняет локальный профиль, но блокирует доступ и переживает restart.
15. Resume возвращает тот же peer.
16. Delete отдельно подтверждает отзыв доступа и удаление локального файла.
17. Rotate создаёт новую пару ключей и отзывает старую.
18. Показываются handshake, endpoint, RX и TX.
19. Показывается предупреждение, что online — эвристика.
20. Есть `--dry-run` и `--json`.
21. Каждая mutation создаёт временную recovery-копию и удаляет её после успеха или
    проверенного rollback.
22. Искусственная ошибка вызывает автоматический rollback.
23. Full-tunnel профиль в тестовой среде получает внешний IPv4 сервера.
24. Эталонный Office 308 профиль после подключения показывает `94.200.113.114`.

## 29. Инструкции AI-агенту, реализующему проект

1. Сначала создать архитектурный документ и threat model ключевых операций.
2. Не начинать с TUI: сначала реализовать тестируемое core API и read-only discovery.
3. Отделить слои:
   - domain model;
   - SSH transport;
   - remote OS adapters;
   - WireGuard parser;
   - transaction engine;
   - local profile vault;
   - CLI;
   - TUI.
4. Все команды должны иметь структурированный request/response, чтобы TUI и CLI использовали одну логику.
5. Ни один UI-компонент не должен напрямую выполнять shell-команды.
6. Начать с Ubuntu/Debian и Fedora; unsupported system должен давать понятный read-only отчёт, а не угадывать mutation.
7. Перед реализацией writer собрать corpus реальных WireGuard configs.
8. Для каждого исправления parser добавлять regression fixture.
9. Никогда не подставлять пользовательское значение в shell string без безопасного протокола передачи.
10. Никогда не логировать полный stdout команды, которая потенциально содержит key material.
11. Сделать secret redaction центральным обязательным слоем, а не набором случайных вызовов.
12. Mutation API по умолчанию работает как plan/dry-run; apply — отдельный шаг с fingerprint плана.
13. Проверять изменения на VM, а не на пользовательском production-сервере.
14. Не использовать Office 308 как площадку для первых destructive integration tests.
15. Не выполнять package install, firewall change или restart без отдельного подтверждения.
16. Документировать все оставшиеся ограничения честно.

## 30. Открытые решения перед реализацией

Пользователь/разработчик должен подтвердить:

1. Окончательное имя приложения и команды. — **`wgtui`** (без дефиса, используется без изменений по всему документу — пути, CLI, идентификаторы).
2. Нужны ли обе локализации в MVP или сначала русский интерфейс. — **только английский** (см. п.1 ТЗ).
3. Разрешён ли optional `/etc/wireguard/.wgtui-meta.json`. — **нет**. Удалённые несекретные метаданные (п.16.2) не реализуются. Настройки и локальный реестр приложения хранятся в домашнем каталоге пользователя, запустившего клиент (п.7.3, п.16.1).
4. Нужно ли шифровать локальное хранилище профилей отдельным master password или достаточно filesystem permissions. — **нужно шифрование**. При первом запуске приложение задаёт master password; локальное хранилище профилей (п.7.3) шифруется им в дополнение к правам `0700`/`0600`.
5. Нужно ли использовать OS keychain для путей/секретов в первой версии. — **нет**. Всё хранится локально в домашнем каталоге пользователя, запустившего приложение (шифрование — см. п.4 выше).
6. Какие дистрибутивы кроме Ubuntu/Debian/Fedora обязательны для MVP. — **только эти три** (опечатка в первом ответе: macOS — платформа исключительно управляющего клиента, не сервера, согласно п.5.2).
7. Должен ли мастер установки автоматически настраивать firewall или только генерировать проверенный план. — **автоматика с планом и подтверждением**, как уже описано в п.13.5: определить backend, показать план правил, применить только после явного подтверждения.
8. Нужен ли preshared key по умолчанию. — **да, включён по умолчанию** при создании peer'а.
9. Нужна ли поддержка срока действия peer как локальной политики без server daemon. — **не нужна в MVP**, может быть добавлена позже.
10. Нужно ли приложение уметь активировать созданный профиль на той же машине или только управлять сервером и экспортировать профиль. — **только управление удалённым сервером** и экспорт профиля; активация профиля на локальной машине не входит в задачи приложения.
